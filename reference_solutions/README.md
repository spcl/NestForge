# Reference solutions

One file per benchmark, `<kernel>.py`. Its `solve(s, ctx)` applies the reference moves; replay times the result against `default_moves()` and checks it against the bench oracle.

```
python -m nestforge.replay reference_solutions/<kernel>.py
```

**Adding a solution:** keep the script short, like `tsvc_2_s231.py`: the kernel, the config and the moves, picked by kind and by what they read and write. Add a kernel here once its moves beat the default by more than the timing noise (10-17% between Daint nodes). CI replays every file here at preset S on one CPU thread (`tests/test_replay.py`), so a solution that stops applying or no longer matches the oracle fails the build. A script that cannot run on the pins yet sets `CI_SKIP` to the reason, and CI skips it. If the route uses one of the candidate new stage 2 moves, say which row of the move ranking it is (the table of built and missing moves, ranked by the kernels each would unlock), so every benchmark cites the same table and a move that is not in it gets a row first.

All 19 benchmarks, the latest measurement of each. Preset M on a Daint GH200 node unless the row says otherwise; every variant matches the bench oracle. **Pins** is the NestForge commit the numbers were taken on: `1309709` is this branch (DaCe `98482ac25`, HPCAgent-Bench `ed1f78857`); a row on older pins has not been re-timed here yet; `aes_graupel` was re-timed on `c2daa40` (DaCe `7c06b5194`, HPCAgent-Bench `b9f24cc4d`); `permute_3d` and `warpx_boris_push` were timed on `690de2f` (the same DaCe and HPCAgent-Bench pins). Whole-program times taken on a NestForge with `5a0dea6` but not `c2daa40` (2-4 Nov 2026, e.g. `bc07961`) ran every OpenMP thread on one core (#75); no row here is from that window any more. **CI** says whether `tests/test_replay.py` replays the file at `cpu:1:S`.

`aes_graupel` beats the default: 930.7 ms to 509.0 ms at preset M, 72 threads, on `c2daa40`, oracle ok (job 5256868, 5 reps). It was 0.89x on `1309709` (jobs 5197631 and 5197819) and 7.54x on DaCe `3469167e5`. Two runs on `bc07961` gave 1.90x and 1.89x (jobs 5246786, 5253180), but at 72.0 s and 70.5 s: those ran on one core (#75), so only their ratios agree. Why the split wins, from the structure at preset S (no build): the rate-limiting loop over the 6 species in each level (`for iqx in range(NX)` in `microphysics_level`) is one map of range `0:6` whose body holds the per-column maps. The default leaves it as it is, so only 6 iterations run in parallel and the column maps inside run serially. `doall-fission` distributes that species map over each statement of its body, and the default then collapses each piece with its column map into a two-dimensional map, `0:6` by the columns (16 of them), so all 72 threads have work. One species-only map stays (the `dqdt` update). Taking no move also keeps the 6-wide map, but skips the default's other moves, and that alone is faster than the default (675.8 ms, 1.38x, job 5256868); the split beats it by 1.33x, above the node noise, so the gain is the split's and not only what the default gets wrong. The gain is below the parallelism ratio because the rest of the level (`process_rates` and the sedimentation) is unchanged.

How to reach it: the order matters. `doall-fission` goes first, on the fresh program: it is the move the stage 1 menu offers on the map writing `sink` and `sx2x` (next to 1067 `doall-fusion`, 808 `tile-doall`, 14 `set-library-implementation`, 11 `expand-library`, 7 `expand-doall` and 6 `subgraph-fission` offers), and `default_moves()` runs after it to collapse the pieces. The default alone never splits that map. Two decoys: taking no move, 675.8 ms (1.38x at M, 72 threads, on `c2daa40`, job 5256868), declared in the script as `stage1`; and the same split after the default instead of before it, 1.18x (job 5253180, on `bc07961`, so timed on one core (#75); only the ratio is kept, not retimed). The move is still offered after the default, but why it pays less there has not been inspected. That second decoy is not in the script, because replaying it at `cpu:1:S` pushes the CI test past 25 minutes. Not checked yet: the 6 `subgraph-fission` offers.

`bfs` is close to "take no move", so treat it with care. On the GPU the default itself interchanges the source-vertex loop of `frontier @ graph` into the target-vertex map, which leaves the N = 1200 threads of preset M each summing a whole column alone; the reference undoes that interchange. Taking no move and skipping the default's fusions is almost as fast: 410.1 ms, 3.45x, so the reference beats it by only 5%, within the node noise. The kernel is kept because a real move beats the default (as for `bellman_ford`), but its gain mostly measures what the default gets wrong on the GPU, not what the move adds. On the CPU the default keeps the loop outside and leaves the opposite move (`interchange-for-doall`), which is slower there (0.84x in the screen), so the reference is the default; the script declares the no-move variant as a decoy (`stage1`).

`fuse_physics_into_scan` also declares a decoy: the reference, then the physics map interchanged so the levels are outermost, which leaves only the 90 levels parallel on the GPU (300 ms, 0.05x of the default).

`harris_corner` was timed with the per-kernel check against the emitted Python skipped (moves, scopes, placement and kernel builds once, then the whole program against the bench oracle): that check runs the fused kernel as a Python loop over every point, hours at preset M, so a plain `python -m nestforge.replay` of this file at M is very slow. On the CPU the same route is slower than the default (0.75x at 2048 x 4096, DaCe `0f8ac0227`), so the reference there is the default.

`cholesky2` replays in CI (since `1cf0305`; it was skipped while the Python emitter wrote a tasklet's `conj` as a bare name: `NameError: name 'conj' is not defined`, also seen on `quatrex_rgf`); the timings above check the whole program against the bench oracle. It depends on the device: on the GPU the same `expand-library` takes 9.5 s against the default's 8.5 ms (the vendor solver), so the GPU reference is the default and the expansion is its decoy; on the CPU the decoy is `set-library-implementation` to OpenBLAS, which times like the default (22.3 s). The CPU default's 22 s (about 1 Gop/s for the factorization) is far below what OpenBLAS reaches on one core, so part of this gain is the library setup on Daint, not only the schedule; the default still takes that path.

`pagerank` needs both expansions: expanding only the product fails to build (`KeyError: '_out_gemv'`, the same error as `atax` after expanding its products), so that half-route cannot be listed as a decoy. On the GPU the default does not build (`CompilationError`), while the two expansions build and run (148.5 ms, oracle ok); the GPU becomes a configuration once the default builds there.

`hmm_forward` takes the same route as `pagerank` on another program (forward probabilities of a hidden Markov model): one family, two kernels. Its GPU default does not build (`CompilationError`), so the GPU is not a configuration yet.

`cloudsc_nproma` is CI-skipped: the kernel is not in HPCAgent-Bench `main` (it came with spcl/HPCAgent-Bench#124, which was reverted; its files are at bench commit `d22922c5c`), and on DaCe `7683e143` its `doall-fission` reads and writes `pfplsx` through one access node, a cyclic state that the stages after fusion reject (`NetworkXUnfeasible` in `route_ordering_through_data`). On main the default still leaves the route on the menu. At 72 threads the route was 1.19x at preset M and 2.04x at `NPROMA` 1024 (older pins).

`floyd_warshall` needs `snapshot-reads` before the default. Each step computes `outer = path[:, k] + path[k, :]` in one doall and `path = min(path, outer)` in another; the first reads `path` and the second writes it, so the default cannot fuse them and writes the N x N `outer` every step (take-no-move is the same time, 0.98-1.01x at M, and the menu offers only `tile-doall`, `expand-doall` and `tile-for`). `snapshot-reads` copies the two slices into vectors, in a doall of its own because a plain copy is folded back into a read of `path` by the cleanup that follows every move; the first doall then reads only the vectors and the default's `doall-fusion` removes `outer`. The gain depends on the size: 0.82x at S (1.56 ms against 1.90 ms: the vectors cost more than the traffic saved), 1.27x at M (N = 1800, `outer` is 13 MB), 1.65x at XL (N = 3855, 59 MB; 246.70 ms to 149.20 ms). The cache reason is a hypothesis, no counters were read. One process, bench default and the move's route built once each and timed alternately (bench, move, move, bench, bench, move; 5 reps each, not the 10 of the catalogue's G4), 72 threads, graded against a NumPy loop with an exact `int32` compare (the bench's compiled reference takes about 25 minutes per process at M, so it was replaced by the NumPy loop of the same semantics); every run correct. Job 5312612, node `nid005763`. A hand-written program with the same snapshot, timed the same way on two other nodes, gave 1.24x and 1.26x at M and 1.64x at XL (jobs 5312468, 5312474), so the move reproduces the prototype. A second node (job 5312684, `nid005341`) gave M 31.68 ms to 25.28 ms (1.25x) and XL 247.58 ms to 150.20 ms (1.65x), every run correct. The reference's script has one decoy, `stage1` (no move, no default fusions), which is the default's time.

`conv2d_group_norm_scale_max_pool_clamp` runs only on a DaCe with two fixes the pin `7c06b5194` lacks, so it is CI-skipped. Without the first (spcl/NestForge#86, fork commit `845c931cf`) the SDFG fails DaCe's edge validation after canonicalization: the first max-pool tap is a strided slice with the symbolic step `maxpool_kernel_size`, and the check cannot prove its element count equals the destination's without the scope's facts. Without the second (the TTGT temporary of a sliced operand, spcl/NestForge#74, fork commit `cc9642937`) the default overran the `ttgt_left_transposed` buffer of the tap contractions and aborted at preset M with `corrupted double-linked list` (spcl/NestForge#87; AddressSanitizer jobs 5314220 and 5314231; with only the first fix the default also segfaulted once in a standalone run before the screen). With both, the default builds and matches the bench's NumPy function in float64 at rtol 1e-8 (the bench's torch oracle is missing, T46-74; the NumPy function rejects a zero, shuffled, doubled, flipped and channel-reversed convolution at S and M, `conv2d_oracle_sensitivity.out`). After the default, the nine taps are `TensorDot` calls that DaCe lowers to a transpose, a GEMM and a transpose; `expand-library` on that node turns each into one parallel loop nest that reads the padded window in place: 63.74 ms to 45.62 ms at M, 619.02 ms to 393.08 ms at L (job 5314407, node `nid005667`, one process, 12 runs alternated default, route, route, default, and so on, 5 reps each, every run correct, no crash in either program); the same route was 45.29 ms against 63.75 ms (1.41x) in the single-move screen of job 5314246 (node `nid006010`, 3 reps). Decoys: `stage1` (no move, no default fusions) is 65.04 ms, the default's time; the `pure` implementation of the same node is 437.78 ms (0.15x). The other single moves after the default (`doall-fission`, `subgraph-fission`, the other library expansions, `copy-to-doall`) are 63.8-71.5 ms, and `copy-to-doall[state14]` is incorrect. It is the same lever as `cholesky2`, `hmm_forward` and `pagerank` (a library call replaced by NestForge's own loops), on a convolution. The cause of the gain is not measured; the explanation (no transposes and no GEMM call) is from the structure of the code. Only the CPU at 72 threads was timed.

`velocity_tendencies` is not a menu move. After `default_moves` the edge phase (the nests that write `vt`, `vn_ie`, `z_kin_hor_e`, `z_vt_ie`, `z_w_concorr_me` and `z_v_grad_w`) is one kernel, and that kernel's source is rewritten so one OpenMP loop over tiles of 64 columns holds every level loop of the phase. The default strip-mines each nest alone, so the next nest reads `vn` and `vt` back from memory. Preset M, 72 threads, mean of 5, oracle ok, job 5194998 on one GH200: 159.52 ms to 118.26 ms, 1.35x, on main `fb130f1` (DaCe `0f8ac0227`, HPCAgent-Bench `e7d161d6f`). A 16-thread login-node run of the same route was 206.89 ms against 448.36 ms in that process. The gather-loop interchanges and the subgraph cuts were slower than the default.

`permute_3d` (a 3D `A.transpose(...)`) needs both moves, in order. The default keeps the transpose as one library call (HPTT). `expand-library` alone turns it into NestForge's loops, which time like HPTT (0.98-0.99x, declared as the decoy `expand-only`); `tile-doall` on the expanded map with 16 per dimension then gives 3.40x. The tile edge matters: 256 per dimension is slower than the default (0.35-0.39x, the decoy `large-tile`), and 64 gave 1.73x on `c2daa40` (not re-timed). The reason given in the script (a 16^3 block of `A` and of `B` stays in cache, so the strided side stops missing per element) follows from the sizes; no cache counters were read. Job 5303150 (preset M, 72 threads, 5 reps per variant, 3 rounds alternated with `warpx_boris_push`), oracle ok for every variant.

`warpx_boris_push` uses a move that is only on this branch, `interchange-for-doalls` (row 1 of the move ranking, the lane hoist; row 12, the hoist over guarded maps, had listed this kernel, but the plain row 1 move applies). It pushes each particle through `nsteps` steps of elementwise maps; the default keeps the step loop outside, so each step reads the particle and field arrays again, and the move puts the step loop inside one particle map. Preset L, because the gain is measured there (job 5303150, 3 rounds, 1.59-1.60x; 1.49x in job 5280781); preset M was not timed for this row. The decoy `stage1` (no move, no default fusions: one parallel region per map and step) is 0.45-0.46x. The same job on the DaCe fork copy `e4ba73236` gave 1.60x, so the gain does not depend on the fork's changes.

`column_scan_nlev_nproma` is a stage 3 benchmark: its lever is where the kernel boundary sits, not a stage 2 move. The kernel scans each column down its levels, `nsteps` passes in a row. After the default the step loop stays on the host and every pass launches the level loop as its own kernel, because the default scopes open a loop only when its body is parallel maps (`opened` in `stages/scopes.py`) and the level loop holds the `k == 0` branch. `Script.scope` (`Session.set_scope`) makes one kernel of the whole step loop, with one parallel region inside it. The peel of the first level (`peel-for`) and a `tile-for` of the step loop give the same layout by accident: the peel wraps the body in a guard and the tile adds a loop level, either of which the default scopes refuse to open (control file in job 5306973: scope 1.14x, 1.26x, 1.27x; peel 1.17x, 1.15x; tile 1.19x, 1.22x, 1.27x, so the three are one route within the noise). `peel-for` alone gives no gain before the default (decoy `peel-first`, 0.82-1.18x) and making the level map sequential is slower (decoy `level-map-sequential`, 0.94-1.10x). Preset M, 72 threads, 5 reps per variant, oracle ok everywhere, job 5306973 (CI replay at `cpu:1:S`: every variant ok, reference 2.41x at one thread). The gain is the smallest of the set and sits at the 1.17 bar. Job 5306973 (node `nid005802`) gave 1.20x, 1.39x and 1.30x, but its default varied from 8.7 to 10.2 ms between rounds while the reference stayed at 7.1-7.3 ms; job 5311088 (node `nid005343`) gave 1.18x, 1.18x and 1.19x with a steady default (7.9-8.0 ms against 6.65-6.77 ms), oracle ok. Read the gain as 1.18-1.20x. Decoys on the quieter node: `peel-first` 1.01-1.03x, `level-map-sequential` 0.94-0.95x. The partner `column_scan_nproma_nlev` (other layout, same step-loop structure, job 5311088) gains only 1.09-1.11x from the same scope (default 4.9 ms, scope 4.45-4.48 ms), as from a `tile-for` of the step loop (1.09-1.10x), and the peel is slower there (0.65-0.69x), so the scope is the layout-independent lever, the peel is a trap in one layout, and the partner is below the bar and counts with this kernel as one family.

`conv3d_group_norm_mean` (a Conv3d, a GroupNorm and a mean over all but the batch) is CI-skipped and graded against the bench's NumPy reference, because the bench's own oracle is KernelBench's torch model, which the pip install lacks (every variant would run unchecked). That oracle also could not see the convolution at M at its tolerance (rtol 0.03, atol 0.01): GroupNorm removes each group's mean, so a zero convolution, doubled weights or a flipped kernel all pass. The timings use `conv3d_group_norm_mean_numpy` in float64 at rtol 1e-8 and atol 1e-10, which passes a reordered computation (3e-15 off) and fails a flipped kernel (1.4e-2 off). After the default, the kernel-position loop is the innermost loop of the convolution and each output point calls it as a function that adds one product to the accumulator in memory; `interchange-doall-for` on the output-point map and that loop puts it outside the five output maps, so the innermost loop is the output width, a contiguous `omp simd` loop (read from the generated code of job 5303945, no counters). Preset M, 72 threads, 5 reps per variant, job 5303945: default 1646.9 and 1644.3 ms, reference 1244.2 and 1234.0 ms, 1.32x and 1.33x; the third round crashed (signals 11 and 7), and so did the default at preset S, so it is not clear that the crashes come from the route. The decoy `stage1` (no move, no default fusions) is 0.74-0.75x. The gain is above the 1.17 bar in both rounds, but the row rests on two rounds on one node; a second node and a third round would settle it, and the script has no tile decoy because the earlier tile timings (job 5281632) were not graded against a trusted reference.
